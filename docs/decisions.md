# Implementation decisions

The v0.2 documents in `specs/` preserve the source product and architecture. These decisions supersede their older recommendations:

- **MIT:** All first-party platform, protocol, CLI, runner, frontend, prompts, and conformance code is MIT licensed. Dependencies, papers, datasets, and submitted artifacts retain their own declared licenses.
- **Fly.io application hosting:** The public Next.js app, Go API and Go worker are separate processes on Fly.io. PostgreSQL and object storage remain external persistent services. No application filesystem is a source of scientific state.
- **PostgreSQL 17 and Tigris:** A dedicated Fly Managed Postgres cluster holds transactional state and the queue. A private S3-compatible Tigris bucket holds immutable content-addressed bytes. Public visibility is granted by the application after the relevant database transaction, never by making the private origin bucket public.
- **Separate validation infrastructure:** Dedicated Linux amd64 verification hosts run the Firecracker/Jailer contract. The application cannot execute a validator, and a missing trusted runner is a visible unavailable state.
- **Single-host platform verification (September 4, 2026):** New MVP challenge versions default to the explicit `platform` verification policy. One dedicated physical host can complete preflight, publication, and score adjudication, including milestones and public-frontier advances. Fresh-VM repeatability, isolated execution, pinned checker inputs, signed receipts, and exact score arithmetic remain required. `platform_verified` and `independently_replicated` are separate assurance statuses. A second physical host is required only when the locked policy is `independent`; two guests on one host never count as independent replication. Policy is immutable in the challenge lock. Previously locked contracts with an omitted policy retain their original independent-confirmation meaning.
- **Single Go module:** The source shares one Go module because the former split-license boundary no longer exists. The protocol package has no dependency on the platform database or hosted application.
- **Launch posture:** Public browsing, invited writes, capped validation, and no payments. The seeded demonstration is distinct from the externally reviewed invitation pilot. A real agent attempt is not an independent scientist, a completed pilot, or evidence of a new scientific discovery.
- **Meaningful scientific progress (September 7, 2026):** Every ranked metric in a new challenge must have a defensible connection to its scientific or applied-science objective. Require the metric's interpretation, supporting evidence, preserved conditions, meaningful improvement threshold, proxy-gaming analysis and limits of the permitted claim. A reproducible score alone is insufficient. The [metric policy](scientific-metric-policy.md) and [creator worksheet](templates/metric-rationale.md) make this an explicit design/review requirement. They do not retroactively change existing locks or claim automated proof of relevance.
- **Validation coverage (September 7, 2026):** The [Yukon audit](research/yukon-validation-audit-2026-09-07.md) found that the current Python/data-only profile does not cover the full public portfolio. The [extension requirements](specs/validation-v0.3.md) define proof, submitted-program and hardware-measurement capabilities, richer metrics and staged evaluation as the target architecture. These capabilities are not implemented or enabled by the specification. Distinct evaluator/candidate isolation and independent proof checking do not themselves require different physical hosts; the existing single-host policy remains in force.

ECDSA P-256/SHA-256 DSSE, exact tick arithmetic, immutable locks, all-crossed milestones, receipt ordering, private losing artifacts, clean execution, and the external launch gates remain unchanged. The single-host decision supersedes mandatory cross-host confirmation for new `platform` policy challenges in the historical v0.2 specifications.
