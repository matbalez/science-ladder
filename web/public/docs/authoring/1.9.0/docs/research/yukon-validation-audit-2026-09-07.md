# Yukon validation compatibility audit

Checked 7 September 2026 against Science Ladder commit `5a4b08d4043f0b83a479516445a95ce3e512238a`.

## Finding

**The deployed framework is not yet broad enough for Yukon's full challenge portfolio.** Its reusable control plane is a good foundation, but its only execution profile deliberately excludes submitted programs, native proof tools, hardware-dependent timing and richer result evidence. A generic Python entrypoint does not make those capabilities available.

The [public directory](https://www.yukon.org/) was cross-checked against the anonymous [public benchmark registry](https://api.yukon.org/api/benchmarks). The registry returned **27 entries: 10 open, 13 closed and 4 failed**. Twenty-one are the current/retired competitive entries discussed below; six are historical/test registrations, all retained in the appendix. This catches retired Laguna and Qwen tracks that the homepage alone misses. Exact registered source commits were inspected, rather than treating whichever commit is now on `main` as the historical contract.

The [machine-readable inventory](yukon-validation-inventory-2026-09-07.json) records every ID, status, source commit, evidence link, validation design and capability gap. This is complete for the returned public registry, not a claim to have recovered deleted/private history. The source repository also contains interactive and symbolic-regression tasks absent from that registry; their mere presence does not establish that Yukon listed them. They are not counted as past public challenges.

This was a source/contract audit. No Yukon candidate code, setup script, proof or benchmark was executed, no private workload was accessed, and no solve or Discussion was submitted. Published infrastructure security and numeric records were not independently certified.

## What Science Ladder actually supports

At the audited commit:

- [`ValidateManifest`](../../pkg/protocol/validate.go) admits only `artifact-checker-v1`, a direct Python checker, CPU classes, at most 4 vCPU, 8 GiB and 600 seconds. Artifact paths/extensions are data-only and uploads are capped at 64 MiB.
- The [builder](../../internal/runner/builder.go) rejects native binaries and arbitrary build scripts, accepting only the declared pure-Python dependency profile. Renaming a proof/program extension does not supply a compiler, trusted kernel or safe program-execution boundary.
- [`Metric` and `ValidatorResult`](../../pkg/protocol/types.go) carry one primary scalar and Boolean gates. Scalar composites can be computed by a checker, but there is no generic typed metric vector, proof-bound parameter record, per-case measurement record, Pareto policy or separate scientific-achievement predicate.
- [`ConfirmScores`](../../pkg/protocol/scores.go) compares two scores to a declared tolerance and keeps the conservative result. That is not a performance-study estimator or a statistical promotion policy.
- [Hidden suites](../../pkg/protocol/hidden.go), immutable locks, signed receipts, separate execution and [scientific review](../../internal/platform/review.go) already exist. Scientific review asks about validity and proxy gaming, but does not require a structured metric-to-goal argument. Encrypted suites do not by themselves isolate a submitted program from its judge.

These are execution and semantic gaps, not a reason to require a second physical verifier. Single-host platform verification remains the default. Distinct proof checkers or isolated candidate/judge processes can run on the same physical server. Apple-specific workloads need Apple capability only if we actually host those workloads.

## Important distinctions exposed by the source audit

1. **Search score versus established result.** Heesch separately exposes completed coronas and partial coverage. The partial term must not earn a complete-corona scientific milestone through rounding. Its external certificate checkers and large proof budgets are additional requirements, despite the fact that its solver submits data rather than executable code.
2. **A proved quantity can still be a proxy.** Proximity's registered source explicitly limits its result to a threshold-induced spot-check quantity for a fixed IRS profile. Its lower and upper predicates differ. The platform must retain the theorem and assumptions behind a displayed unit; a “bits” label is insufficient to claim whole-protocol security. See the [registered target definitions](https://github.com/proximity-prize/proximity-prize/tree/1b2ca03c8b0ad8a53d647f1eb13aa60b928b8a2c/ProximityPrize/Benchmark).
3. **Correctness criteria vary by contract.** The Gemma participant contract permits a token-divergence budget, whereas the retired Qwen scoring contract specifies exact-token reverification. A common speed leaderboard must not imply identical quality guarantees. Whether the permitted difference preserves useful application quality remains an additional scientific question.
4. **Aggregation and references are scientific choices.** Matrices uses a weighted mean of bucket geometric means, not one global geometric mean. The FrontierCS checkers expose raw objectives and several clipped/unbounded transforms; the registry even reports scores above one for Worldmap and Traveling Santa. A normalized percentage is not a universal distance to an optimum. Formula, aggregation order, selected cases and version must be explicit.
5. **Public descriptions and actual contracts can diverge.** The polyomino registry description mentions a reference ratio, but its pinned checker computes packing utilization. Some MLX documents retain superseded scoring/arming prose alongside later rules. The Qwen manifest's numeric ceiling is 5.0 while older paragraphs still mention 3.0. The registry's Proximity source commit also differed from GitHub's current main during inspection. These are reasons to bind the evaluated contract and record unresolved differences, not to assume that marketing copy is authoritative or infer an exploit.
6. **Generalization depends on the contribution.** A single fixed puzzle/shape can establish a construction claim. It cannot, without more evidence, establish that an algorithm solves a hidden population well. Replacing an OpenFrontierCS program with a table of known answers changes what is being evaluated. Conversely, a narrow but valid mathematical construction does not need a fabricated industrial application to be worthwhile.

## Required direction

The [validation extension requirements](../specs/validation-v0.3.md) separate data, proof, program and measured-performance capabilities and define their composition. They also require named raw metrics, explicit comparison and achievement policies, proof/output binding, larger staged workloads, and matched hardware without reviving mandatory cross-host replication.

The [scientific metric policy](../scientific-metric-policy.md) makes the user's requirement explicit: a ranked metric needs a defensible connection to the goal, preserved conditions, evidence, a meaningful change threshold, a concrete proxy-gaming analysis and a bounded permitted conclusion. The [creator worksheet](../templates/metric-rationale.md) fits into the existing `challenge-brief.md`; it adds no unsupported YAML fields.

The narrow v1 runner is not being loosened by this audit. The new documents specify the necessary work and acceptance tests; they do not install native proof checking, a C++/Rust judge or Apple/Metal execution. The current manifest/result schema and automated review still need implementation work to enforce and represent the richer contracts. No production scoring contract or published result changed.
